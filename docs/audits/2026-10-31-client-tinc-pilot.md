# Клиентский tinc: backend и Linux pilot

Следующий этап: [Tinc в существующем Linux GUI](2026-10-31-client-tinc-linux-ui.md), реализованный после этой первоначальной приёмки.

Дата: 31.10.2026. Это закрытый пилот до 16 устройств, отдельно от существующих VPN-режимов. Соседний Linux UI, его движок и сеть тестовой desktop VM не изменялись. Прототип запускается отдельной командой `quantway-tinc`.

## Реализация

- PostgreSQL хранит отдельные узлы, ключи устройств, выбранную страну, версионное назначение, подтверждённую серверную готовность и историю разрешений. Миграции `0126/0127` только добавляют новые таблицы.
- Device API использует текущий токен устройства и права подписки; node API — отдельный токен каждого сервера. Допуск устройств закрыт allowlist. Backend не хранит приватные ключи tinc или TLS.
- Устройство получает все входы, включённые в пилот. Desktop держит соединения со всеми. Серверный core и отдельная edge-сеть устройства не дают клиенту пересылать чужой трафик. Авторизованный VLESS/TLS до назначенного выхода проходит поверх tinc.
- Выход назначается по стране независимо для каждого устройства. Отказавший выход заменяется в той же стране; смена назначения меняет credentials. Клиент получает назначение после точного ACK документов серверами.
- Только выход считает пользовательские байты. Накопительные счётчики с epoch, версией и московским днём доставляются через постоянный outbox; backend сохраняет high-water cursor и атомарно прибавляет дельту в `traffic_daily`. Повторная доставка не удваивает трафик.
- Сервер проверяет credentials независимо от приложения и запрещает обращения к loopback, приватным/служебным сетям, core, metadata и IPv6. Ограничение адресов дублируется помеченными исходящими сокетами и firewall выхода.
- Разрешения живут не более пяти минут. Потеря API не продлевает доступ. Клиент сохраняет блокировку обычного трафика до явной остановки, сервер прекращает только процессы пилота.

## Проверки до выкладки

`TestBackendRuntimeAndSystemClient` с реальной PostgreSQL, авторизованным API, шестью настоящими серверными runtime и двумя Linux-клиентами с kernel TUN прошёл 46 проверок за 135,72 с. Лог рабочего запуска: `/private/tmp/clienttinc-integrated-prefix76.log`.

Один непрерывный 40-секундный TCP-поток переживает продление обоих настоящих device lease; PID серверных и клиентских туннелей, UUID/version и назначение остаются прежними. При этом backend по-прежнему требует ACK точного нового срока, а не только совпадения конфигурации.

Проверены TCP, UDP/DNS, постоянные связи с тремя входами, независимые страны двух устройств, смена страны через настоящий API, отказ A1 → A2 с сохранением назначения второго устройства, отзыв работающего подключения, истечение при отказе API, блокировка физического обхода и очистка после stop.

Проверки изменённого клиента обходят локальную политику приложения и обращаются прямо к настоящему TLS/VLESS сервера: чужие и невыданные credentials запрещены; обращения к `127.0.0.1`, `10.44.0.99`, core, `169.254.169.254` и имени с приватным адресом не достигают контрольных listener. Разрешённые контрольные обращения доходят.

На всех шести серверах стенда общая и физическая пересылка IPv4 остаётся выключенной. Пересылка включена только у собственных `qctcore/qceXX`. Существующие политики DROP, handles правил и контрольный сервис сохраняются при работе и очистке пилота. Дополнительно сохраняются адрес, маршрут `10.66.0.0/16` в отдельной таблице, policy rule, sysctl и контрольный PID старого AWG-подобного layout. Это воспроизводимый layout на стенде, а сохранность настоящих VPN-процессов проверяется отдельно на рабочих узлах.

Fixture также проверяет реальные положительные счётчики обоих устройств, равенство `traffic_daily` сумме сохранённых cursor и отсутствие пользовательского учёта на входах. Отдельные backend/API/accounting тесты выполнялись с реальной PostgreSQL и race detector, без пропусков. Дополнительный regression проверяет продление с теми же UUID/version: новая точная версия разрешения должна быть подтверждена узлом; выдача клиентского документа сама не продлевает историю; блокировка устройства запрещает продление.

Образ после выбора свободного диапазона: `vpnshop-clienttinc-control:b4d321ff1035dd0a-amd64`; затем для GUI добавлен read-only device catalog в `vpnshop-clienttinc-control:cd750328e26d28f2-amd64`. Публичный путь: `https://qntw.link/api/client-tinc/`. Другие пути обрабатывает прежний сервис.

Основные контейнеры shop/postgres сохранили прежние ID и время старта, магазин отвечает HTTP 200; запрос без токена к новому API получает 401.

Серверный runtime устанавливается отдельной службой `quantway-client-tinc`. Свои префиксы `10.76.0.0/24`, `10.77.0.0/16`; core TCP/UDP 17444; edge 17445–17460; внутренний TLS 18443; StatsService только loopback 18444. ## Живой пилот и приёмка

Включены пять отдельных runtime: входы `in-pl`, `in-nl`, выходы `out-pl`, `out-pl-2` и `out-se`. Все пять подтвердили точный applied revision через публичный HTTPS API. Старые процессы tinc/Xray на каждом узле сохранили PID и время старта. Сохранились прежние правила, handles и политики firewall; динамические адреса Fail2ban сравниваются отдельно от статических правил. Общий forwarding и forwarding физических/старых VPN-интерфейсов остаются `0`.

Linux ARM64 прототип проверен через настоящие рабочие узлы в отдельном Docker network namespace. Контейнер получил только дополнительные NET_ADMIN/NET_RAW и `/dev/net/tun`, без privileged/host-network. Проверены:

- Системный HTTPS-трафик через польский выход `199.19.77.43`, затем шведский `185.130.44.165`, затем снова польский. Оба входа оставались подключены.
- Непомеченные пользовательские UDP/DNS запросы к `1.1.1.1` проходили через системный TUN в обеих странах.
- Явная остановка удалила оба TUN, собственную nft-таблицу и маршруты, восстановила обычную сеть только тестового контейнера. Контейнер удалён; private identity сохранена в отдельном named volume для повторного запуска.
- В production PostgreSQL у тестового устройства появились реальные байты. На момент проверки: PL — 5 019 вверх / 15 727 вниз; SE — 2 524 вверх / 7 895 вниз. Значения `traffic_daily` точно совпали с суммой накопительных cursor. На обоих входах и неиспользованном резервном выходе пользовательских байтов нет.

Для canary создано одно анонимное тестовое устройство с одним явно записанным днём manual grant; контактных адресов и получателя уведомлений нет. Credentials находятся в закрытых файлах и не входят в артефакты или отчёт. Массовый допуск устройств не включался.

Живой тест не отключал серверы и не создавал аварий на проде. Отказы выхода/API, отзыв, подмена credentials и внутренние назначения проверены на изолированном полном стенде. Соседние UI/VM и сеть компьютера не менялись.

Устаревшие и финальные временные установочные каталоги на узлах удалены после установки; действующие бинарные файлы, ключи, state и резервные копии сохранены. На серверных процессах действуют ограничения CPU/памяти; до подключения тестового устройства runtime занимали около 9–10 MiB каждый.

## Артефакты и ограничения

Сборки Linux находятся в `bin/quantway-tinc-linux/quantway-tinc-linux-{amd64,arm64}.tar.gz`, рядом `SHA256SUMS`. В архиве есть CLI, guarded native tinc, лицензия, инструкция и сведения о сборке. Credentials и state в архивы не входят.

Это CLI-прототип с root и полным IPv4 VPN. Пользовательский IPv6 блокируется. GUI и отдельный root helper впоследствии подключены в следующем этапе по ссылке выше. Перенос доменных исключений, production crash recovery и смена физической сети остаются следующими этапами. Полный Android TUN и Apple/Windows платформы не подтверждены этим Linux-тестом.

Сегментация отдельным edge-процессом на устройство/вход ограничена 16 устройствами и не рассчитана на массовый запуск. При смене входа или выхода существующие TCP-сессии могут оборваться. Мобильная динамика входов, нагрузка и расход батареи остаются отдельным этапом.

Откат: `deploy/tinc-client/rollback-control.sh` убирает только новый API-путь и останавливает только sidecar; `systemctl disable --now quantway-client-tinc` выключает runtime конкретного узла. Общую БД и обычные VPN-службы откат не трогает. Ключи и конфигурации доступа остаются в закрытых файлах.
