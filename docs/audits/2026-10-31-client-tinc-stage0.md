# Клиентский tinc: первый технический срез

Дата: 31.10.2026. Статус: изолированный прототип этапа 0. Основной VPN-клиент и
production-парк к нему не подключены. Linux-интерфейс, над которым работает
соседняя сессия, этим срезом не изменяется.

Основание: [спецификация](../superpowers/specs/2026-10-31-client-tinc-layer-design.md)
и [план](../superpowers/plans/2026-10-31-client-tinc-layer.md).

## Что добавлено

| Часть | Реализация |
| --- | --- |
| Политика | `internal/clienttinc`: полный каталог входов, разные активные наборы ПК/ТВ и телефона, сохранение здорового выхода, замена в той же стране, проверка устройства/ключа/версии/срока разрешения |
| Native | `mobile/native/tinc` и `mobile/scripts/build-client-tinc.sh`: закреплённые исходники, Android NDK/API, fail-closed socket guard, числовые внешние адреса и manifest сборки |
| Пакетный мост | `mobile/tincbridge`: SCM_RIGHTS broker, fd 3, запуск/остановка дочернего процесса, срок доступа и отмена контекста |
| Android fixture | `mobile/tincbridge/android-spike`: отдельный target35 APK с исполняемыми файлами в nativeLibraryDir, отдельная проверка VpnService/физической сети |
| Сетевой стенд | `test/clienttinc`: реальные tinc/Xray и сетевые namespaces; два устройства, три входа и выходы A1/A2/B1; внешний HTTP/DNS-наблюдатель |

Пакет политики не является API или серверным enforcement: его grant должен
использовать доверенный сервис, независимо установивший identity устройства.
Проверка структуры grant не аутентифицирует сетевого отправителя.

## Решения, которые проверяет прототип

В малом стенде каждому устройству выделен отдельный tinc edge: устройство и
его серверные входы. Edge-процессы входов знают только свой host и этого
клиента и используют TunnelServer/StrictSubnets. Общий core состоит только из
серверов. Это даёт проверяемую границу между клиентами без выдачи им общего
графа и ключей серверного core.

Пользовательский трафик переносится авторизованным внутренним VLESS-потоком
с TLS до назначенного выхода. У каждого выхода собственный сертификат тестовой
CA; клиент проверяет CA и имя, `allowInsecure` не используется. Право другого
устройства не появляется из знания IP выхода. На входе нужен контроль source по edge-интерфейсу до conntrack и
запрет доступа к overlay через публичный underlay; эти проверки не заменяет
локальная конфигурация клиента.

Первый реальный отказ входа выявил проблему обратного маршрута: core мог
отправлять ответ на вход, уже потерявший клиентскую связь. Для малого стенда
использован SNAT внутреннего потока в адрес входа. Новые потоки после смены
входа восстанавливаются до того же выхода. Старое внутреннее TCP-соединение
при изменении NAT-пути может оборваться. Это ограничение, а не доказательство
бесшовного переключения действующих сессий.

## Проверки и наблюдения

- `go test -race ./internal/clienttinc` и `go vet ./internal/clienttinc` прошли.
- Host-проверки `mobile/tincbridge` с `-race` и `go vet` прошли: реальные
  SCM_RIGHTS TCP/UDP sockets, ошибки callback, неправильные/лишние fd,
  приватность guard, отмена и истечение срока процесса.
- C socket guard: 7 тестов прошли, включая IPv4/IPv6, отсутствие/отказ/закрытие
  broker, таймаут и запрет скрытого DNS через libc.
- Собраны отдельные host Darwin/arm64 и Android/arm64 native binaries.
- На исходном TCP relay пути tinc тест четырёх процессов не доставил
  пакет за 25 секунд. С отдельным opt-in патчем тот же тест доставил пакеты
  в обоих направлениях за 5,80 секунды. Патч находится в
  `deploy/tinc-client/patches`; он не меняет сборку служебного меша.
- Linux стенд с UDP/TCP tinc прошёл 53 проверки. Принудительный TCPOnly-прогон
  без relay-патча воспроизвёл отказ доставки после блокировки прямой серверной
  связи: косвенный nexthop уже появился, данные до выхода не доходили.
  С патчем TCPOnly-прогон прошёл полный набор проверок.
- На стенде проверены настоящие HTTP и UDP DNS с наблюдением внешнего адреса,
  A1→A2 с сохранением B1 второго устройства, отказ всей страны A, восстановление
  через другой вход, принудительный транзит через сервер, неверный credential,
  чужой выход, неверное TLS-имя, подмена source, управляющий порт, чужое
  устройство и попытки доступа к overlay через публичный underlay.
- Для малого TCPOnly-стенда измерены 14 процессов tinc и суммарный RSS
  13 204 KiB; итоговый смешанный TCP/UDP-прогон дал 14 692 KiB для тех же
  14 процессов. Это измерение двух устройств/трёх входов/трёх выходов, не оценка production
  нагрузки или потребления телефона.
- Android target35 APK без root выполнил все guard/process/native-тесты.
  Настоящий foreground VpnService создал один TUN; 11 сокетов прошли
  `protect` и `Network.bindSocket`, отказов 0. Raw-IP пакет прошёл через три
  tinc-связи за 0,86 секунды. После прогона тестовый сервис остановлен.
- На Android найдено и исправлено неверное решение выбирать первую Network
  из списка: bind возвращал EPERM. Harness берёт активную физическую сеть до
  создания VPN. Отказ не обходится и приводит к закрытию сокета.

Изолированный Android harness сначала проверял процесс без активного VPN,
затем повторил проверки с реальным VpnService и Java broker. Пользовательские
пакеты через системный TUN в нём не передаются. Shell/data-local запуск не
заменяет проверку упакованного приложения.

Relay-патч включён по умолчанию только в новых экспериментальных сборках и
стенде после сравнения до/после. Флаг со значением 0 сохраняет исходный вариант
для воспроизведения; существующая сборка служебного меша не изменяется.

Команды воспроизведения:

```sh
go test -race ./internal/clienttinc
sh test/clienttinc/run.sh
CLIENTTINC_TCP_ONLY=1 sh test/clienttinc/run.sh
CLIENT_TINC_ANDROID_VPN_GUARD=1 mobile/tincbridge/android-spike/run.sh
```

Подготовка native binaries и платформенных инструментов описана в
`mobile/native/tinc/README.md`, `mobile/tincbridge/README.md` и README стендов.
Флаги исходного TCP-варианта: `TINC_TCP_RELAY_PATCH=0` для Docker-стенда,
`TINC_CLIENT_TCP_RELAY_PATCH=0` для native-сборки.

## Что остаётся открытым

- Прототип создаёт edge-процесс на пару устройство/вход. Масштаб по числу
  устройств, память, количество listeners и скорость ротации не измерены для
  production. Эта схема пока не принята как массовая архитектура.
- Linux namespaces и Android raw-IP fixture проверяют разные части. Полный
  пользовательский TCP/UDP/DNS через один системный Android TUN, split policy,
  смена Wi-Fi/LTE, сон и расход энергии ещё требуют общего теста.
- Наличие активного тестового VpnService и успешного protect/bindSocket не
  доказывает всё пользовательское перенаправление или наследование network
  context для входящих accepted sockets.
- Production API, БД, доставка назначения/отзыва, учёт, выбор по мощности,
  серверные TTL и интерфейс переключения режима ещё не подключены.
- Для Apple проверена только host-сборка Darwin; Network Extension и упаковка
  macOS/iOS не доказаны. Windows и остальные Android ABI ещё не проверены.

Следующий общий data-path прототип должен закрыть Android системный TUN и
внутренний перенос до выхода, затем закрепить сетевой контракт и допустимую
модель масштабирования. Ранний успешный стенд не отменяет эти условия этапа 0.
