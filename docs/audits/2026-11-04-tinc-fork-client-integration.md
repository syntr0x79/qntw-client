# Форк tinc в клиентском слое Quantway

4 ноября 2026. Реализация первого этапа: Linux-серверы клиентского слоя и клиент macOS ARM64.

## Исходники и сборки

Клиентский слой переведён на `syntr0x79/tinc`, commit `03bfd922c1749b27769a3e3a5680efde64d45af0` (`origin/1.1`). Изменение `Preserve private application directories across native lifecycle` опубликовано в форке. Первый исследованный commit `9a9046d6` заменён после воспроизведения ошибки прав доступа на интеграционном стенде.

Native-компоненты собираются Meson из `git archive` закреплённого commit. Каждый комплект содержит соответствующие исходники, лицензию, manifest и SHA-256. Профиль приложения требует socket guard и отключает hooks; серверный профиль сохраняет hooks, необходимые существующему runtime. Первоначальные параметры Linux: batch 1, offload off. macOS сохраняет текущий внешний TCP-режим и VLESS/TLS до назначенного выхода.

Артефакты в репозитории:

- `bin/client-tinc/host-Darwin-arm64-fork/` — native Mac ARM64.
- `bin/quantway-macos-client-fork/Quantway.app` и `Quantway-macOS-arm64.zip` — macOS 0.3.1, build 20261104.1.
- `bin/client-tinc-server-fork/linux-amd64/` и `linux-arm64/` — статические серверные комплекты Linux.
- `bin/quantway-tinc-linux-fork/linux-arm64/` — изолированный клиент Linux для стенда.

Инфраструктурный mesh не переведён на форк. Android/Windows и обычная Linux desktop-упаковка сохраняют прежний источник; Linux fork-клиент выбирается явно через `TINC_CLIENT_SOURCE=fork`. API v1 и схема БД для этого обновления не меняются.

## Исправление приватных каталогов

Новый upstream выполнял `chmod(..., 0755)` для существующего каталога конфигурации при `tinc init` и каждом запуске `tincd`. Первый старт мог пройти, затем socket broker отклонял каталог как неприватный при смене страны. Исходный новый/new стенд воспроизвёл этот отказ после успешной передачи данных и продления доступа.

В форке создание каталогов теперь сохраняет существующие более строгие права и при необходимости сужает избыточные; существующий объект должен быть каталогом. Добавлены проверки init/start/control/reload/stop/restart с настоящим guarded daemon и дополнительные FS unit cases с сохранением всего прежнего набора тестов. Регрессия воспроизводит отказ на первоначальном бинарнике и проходит на новом commit.

В клиентском Go-коде дополнительно проверяются владелец и отсутствие symlink у каталогов идентичности, права восстанавливаются через открытые дескрипторы до чтения идентичности и после init, включая частично неудачную инициализацию. Ключ не перевыпускается. macOS-сборщик использует готовую проверенную пару, без текстового изменения C-исходников, и сохраняет hashes до/после подписи.

## Локальная приёмка

- Native macOS crypto/client: 6 suites, включая реальный lifecycle приватного каталога.
- `tincbridge` с race detector и настоящими native-процессами: packet FD и TCP multihop.
- Go macOS network/privilege, account/subscription/CLI и четыре Swift-теста: прошли.
- Полный пакет `mobile/clienttinc`: прошёл после изоляции теста нагрузки в отдельном процессе. Нагрузка сохранила 1024/1024 UDP-ответа, последующий TCP, пик 26/64 физических TLS-соединений и нулевые постоянные XUDP IDs.
- Проверка native-комплекта: четыре теста, включая изменённые бинарники/исходники и неверный профиль.
- Обновление серверной пары: семь тестов, включая временный pre-exec процесс systemd, неудачный старт и отказ между заменой первого и второго бинарника с восстановлением обеих прежних версий.
- Подпись macOS `.app`: ad-hoc signature проверена. Developer ID и нотариализация не выполнялись.

Linux native suites для ARM64 и AMD64: по 37 успешных проверок и две ожидаемые неудачи, без неожиданных ошибок. AMD64 выполнялся под эмуляцией и не использовался для выводов о скорости. Полный новый клиент/новый сервер прошёл 49 проверок за 175,60 с: 512 МиБ, 100/100 DNS без повторов, 16/16 TLS, продление с сохранением открытого TCP, смена страны, отказ выхода, отзыв, истечение, очистка и точный учёт PostgreSQL. Оба контролируемых смешанных сочетания native-версий прошли по 46 проверок. Данные: [Linux validation](artifacts/2026-11-04-tinc-fork-linux-validation.json).

Проверки интерфейса не были основанием этого обновления: UI не менялся; локальный дополнительный запуск screenshot harness не состоялся из-за отсутствующего Playwright в указанном каталоге зависимостей.

## Первое подключение к production

До обновления серверов новый Mac-клиент проверялся через обычный путь привилегированного помощника с отдельным анонимным тестовым устройством. За семь независимых точек наблюдения пользовательский HTTPS, UDP DNS и системный DNS прошли 7/7, закреплённый HTTPS к контрольному сервису — 6/7. Первый контрольный запрос не прошёл; строгий общий результат этого запуска — отрицательный. Причина единичного контрольного отказа не установлена.

Все измерения фиксировали один системный utun до/после запросов. Отключение подтвердило исходный физический маршрут, прежний набор DNS-ключей, завершение сетевого помощника и native-процесса; обычный HTTPS после отключения вернул 200. Этот запуск подтверждает доставку на смешанной версии клиента/сервера, но не заменяет финальную приёмку исправленного комплекта.

## Ограничение существующей зависимости Xray

Отдельно воспроизведён дефект закреплённой Darwin TUN-реализации Xray: обёртка `os.File` для заимствованного FD остаётся с финализатором; после Close и GC финализатор закрывает дескриптор вызывающей стороны. В повторных тестах переиспользованный номер FD мог закрыть уже следующий пакетный сокет. Воспроизводитель подтвердил действующий FD до GC и EBADF после GC при живой обёртке вызывающей стороны.

Нагрузочная fixture запускается в отдельном процессе, как отдельная клиентская сессия помощника, без изменения её сетевых проверок и таймаутов. Это обеспечивает независимость тестов, но не исправляет зависимость. Перестроение назначения внутри одного процесса macOS остаётся отдельным риском; его надёжность этим выпуском не заявляется. Исправление Xray, аварийная гибель root-помощника, sleep/resume и смена физической сети требуют отдельной приёмки.

Воспроизводитель и результаты сохранены в [Xray borrowed FD evidence](artifacts/2026-11-04-xray-darwin-borrowed-fd.json).

Это ограничение версии 0.3.1 устранено в [macOS 0.3.2](2026-11-04-macos-xray-fd-and-transitions.md): исправленный Xray и переходы PL→SE→PL→другой PL-выход прошли живую приёмку в одном процессе и TUN после принудительной GC.

## Развёртывание

Production-обновление использует `deploy/tinc-client/upgrade-native.sh`. Скрипт заменяет только `tinc` и `tincd`, сохраняет предыдущую пару, проверяет архитектуру/pin/hashes и подтверждает hash реально работающего daemon. Он перезапускает только `quantway-client-tinc.service`; его дочерний Xray также перезапускается, но бинарники агента/Xray, токены, настройки, ключи и unit сохраняются. При ошибке или обрабатываемом сигнале выполняется откат пары.

Первая попытка на `out-pl-2` обнаружила слишком раннюю проверку MainPID службы Type=simple: systemd уже публикует PID, но exec агента ещё не завершён. Автоматический откат вернул старую пару; та же ранняя проверка ошибочно сообщила о неуспешном откате. Независимая проверка подтвердила старые hashes, работающую службу и прежние ключи/настройки. Ожидание исправлено: несовпадающий промежуточный образ процесса повторно проверяется до исходного ограниченного deadline. Добавлена отдельная регрессия. Повторная выкладка на узел прошла, фактический native hash и все 17 core-связей подтверждены.

При сверке первоначального снимка обнаружено событие **до выкладки**: служебный `vpnshop-tinc` на `out-pl-2` завершился с ABRT 10:27:38 UTC (17:27:38 Bangkok), сообщение `Could not read random numbers: Bad address`, и автоматически запустился 10:27:43 UTC. Первая выкладка началась 10:35:44 UTC. Поэтому строгая сверка с первоначальным снимком не подтверждает неизменность всех инфраструктурных процессов/IPv6 link-local/rule handles за всё окно наблюдения. Исходный отрицательный результат сохранён, событие не исключается из отчёта. Перед выкладкой оставшихся узлов снят отдельный актуальный снимок; первоначальный не перезаписан. Причина аварии старого служебного tinc не исследована в этой задаче.

Развёртывание завершено на **18/18 узлах amd64**. На каждом проверены установленная и фактически работающая новая пара, прежние agent/Xray, свежий exact ACK и все 17 аутентифицированных core-соседей. Исходные ключи, токены, настройки и unit сохранены; на узлах оставлены резервные копии прежней пары. Один SSH timeout произошёл до banner exchange на `out-nl`; чтение состояния подтвердило отсутствие изменения, после восстановления доступа узел обновлён последним.

Правила допуска TCP/UDP 17444 с собственным комментарием `quantway-client-tinc:*` пересозданы runtime при перезапуске: expr/comment одинаковы, изменились handles. Они относятся к обновляемому клиентскому слою; исходные before/after наблюдения сохранены. После такого разделения сравнение инфраструктуры **с актуальным снимком перед оставшимися 17 узлами прошло 18/18**. С первоначальным снимком сохранились два отличия: описанный выше ранний crash на `out-pl-2` и изменение динамического SSH address set на `out-se-2`, уже присутствовавшее до его обновления.

Строгая сохранность всех контейнеров магазина за окно наблюдения **не подтверждена**: `vpnshop-shop-1` пересоздан 10:44:42 UTC (17:44:42 Bangkok), изменились container ID/PID/start time. Остальные восемь контейнеров, включая PostgreSQL, совпали со снимком. Команды этой выкладки не обновляли контейнер магазина; причина наблюдаемого параллельного изменения не устанавливалась. Этот результат сохраняется отрицательным, а не исключается нормализацией.

Полная машинная сверка, hashes и оба сравнения снимков: [Production evidence](artifacts/2026-11-04-tinc-fork-production.json).

## Финальная проверка macOS через production

Новая сборка 0.3.1 с исправленным commit подключилась через обновлённый клиентский слой. За полные 45 секунд после состояния Connected все **7/7** независимых точек прошли четыре проверки: обычный HTTPS, HTTPS к заранее разрешённому контрольному адресу с проверкой сертификата, UDP DNS и системный DNS. До/после каждого набора маршрут указывал на один и тот же системный `utun7`. Строгий итоговый результат — `passed=true`.

После stop помощник завершился штатно, системный маршрут вернулся на `en0`, собственные DNS-ключи удалены до исходного состояния, сетевой помощник и tincd завершились. Обычный HTTPS после отключения вернул 200. Анонимный тестовый доступ закрыт командой revoke; последующий запрос каталога с его token вернул 403. Платежи и реальные аккаунты не использовались.
