# Интеграция форка tinc в клиентский слой Quantway

Дата: 4 ноября 2026. Статус: план реализации.

Предлагается заменить источник native tinc в существующем клиентском слое на `syntr0x79/tinc`, сохранив API допуска, назначение страны и выхода, внутреннюю авторизацию VLESS/TLS и учёт. Сначала подтвердить совместимость в TCP-режиме на Linux, затем перенести сборки desktop и подключить Android. Внешний UDP и оптимизации Linux вводить отдельным этапом после проверки полного пути приложения.

## Границы интеграции

Клиентский слой включает приложения и обслуживающие их отдельные процессы `clienttinc-agent`, edge/core клиентского overlay и выходной шлюз. Поэтому план охватывает `mobile/`, `internal/clienttinc*`, `internal/web/clienttinc.go` и `deploy/tinc-client/`. Обновление серверных процессов этого слоя нужно проверять отдельно от обновления приложения.

Инфраструктурный mesh парка (`deploy/tinc/`, `internal/fleet/`, `internal/hostcfg/`, `internal/agent/mesh_tinc.go`) остаётся за границами этого этапа. Общие старые патчи из `deploy/tinc/patches/` перестают использоваться новыми клиентскими сборками, но сохраняются для прежнего инфраструктурного сборщика. Интеграция в Mono/HiddenVPN и другие продукты требует отдельной карты их клиентов; этот план относится к найденной реализации Quantway в vpnshop.

Результат планирования — этот файл. Изменение реализаций, сборка релизов и развёртывание в рабочей сети относятся к последующим задачам.

## Исходное состояние

Форк находится в `/Users/syntr0x/tinc`, изученный commit — `9a9046d650f6e1b741806897a84a68e36e128aec`. Он основан на upstream `211e3dfa` и собирается через Meson. Текущий клиент Quantway закрепляет более старый `release-1.1pre18`, commit `3217d5efb432f5a03beebd5d00b36392ec4b22ef`, и собирается через Autotools с дополнительными патчами. Замены одного URL недостаточно.

План опирается на текущее рабочее дерево vpnshop, включая ещё не закоммиченные компоненты клиентского слоя. Перед реализацией зафиксировать отдельный согласованный срез этих компонентов и исходные артефакты. Посторонние изменения рабочего дерева не включать в коммиты интеграции.

## Что переносится из форка

Форк включает TCP-транзит уже зашифрованных SPTPS records, подготовку сокетов приложения, запрет hooks как опцию сборки, Windows Wintun и остановку foreground daemon через control channel. Это позволяет убрать дублирование патчей в клиентских сборщиках после проверки каждого изменения.

Новый механизм восстановления UDP допускает восстановление только после проверки подлинности пакета. Старый `0001-restart-sptps-on-unverifiable-udp.patch` нельзя накладывать поверх форка: он перезапускает сессию при иной, менее строгой проверке. Сохранить отдельные отрицательные проверки поддельных пакетов, replay и штатного rekey.

Также изменены лимиты использования ключей и периодический rekey, ChaCha20/Poly1305, TCP-буферы, epoll, ограниченное вычитывание пакетных FD и Linux UDP GSO/GRO. Эти изменения требуют регрессии полного приложения, даже при сохранении wire format. Заявленная совместимость протокола ещё не доказывает совместимость нашей смешанной сети и формата ответов `tinc dump`.

Текущие native-конфиги Linux/macOS/Windows задают `TCPOnly = yes`, `IndirectData = yes`, `Forwarding = off`, `StrictSubnets = yes`. Причина TCP-режима зафиксирована в NAT-тестах старой реализации SPTPS. Первый перенос сохраняет эти параметры.

## Целевая схема

Пользовательское приложение → системный TUN → существующая обработка TCP/UDP и правил Xray → VLESS/TLS с credential назначенного выхода → внутренний overlay → native tinc → клиентский вход → core клиентского слоя → назначенный выход → Интернет.

Один контроллер владеет системным VPN, DNS, маршрутами и блокировкой утечек. tinc остаётся отдельным процессом с узким интерфейсом пакетных FD и подготовки внешних сокетов. Ключ устройства хранится на устройстве и переживает обновление native-компонента. Назначение выхода и срок доступа определяет backend.

Обновление tinc не заменяет внутреннюю авторизацию: шифрование overlay само по себе не обеспечивает права тарифа, отзыв, изоляцию клиентов и пользовательский учёт. Существующие отдельные edge-процессы и шлюз допуска сохраняются.

## Этап 1 Закрепление исходников и профилей сборки

Точки изменения: `mobile/native/tinc/source-pin.env`, `mobile/scripts/build-client-tinc.sh`, `build-tinc-linux.sh`, `build-tinc-windows.sh`, `build-macos-client.sh`, `mobile/native/tinc/Dockerfile.linux`, `deploy/tinc-client/Dockerfile.server` и упаковщики исходников.

1. Ввести отдельный pin форка: URL, полный commit, версия Quantway native-компонента. Получать ровно закреплённый commit, экспортировать через `git archive`; локальный `/Users/syntr0x/tinc` использовать только как необязательный источник объектов, без зависимости CI от пути пользователя.
2. Сделать общий подготовщик исходников и Meson-профилей для всех клиентских сборщиков. Убрать повторное применение уже перенесённых socket guard, TCP relay, Android ifreq и Windows hooks/control patches. Сверить Windows backend и guard с существующим вариантом до удаления локальных копий.
3. Заменить Autotools на Meson/Ninja, закрепить инструменты и cross files для Android NDK и LLVM-MinGW. Сохранять версию NDK/API из действующего pin до отдельного обновления toolchain.
4. Перевести macOS на опцию `client_hooks=false` вместо текстового изменения `script.c`. Упаковщик должен брать manifest от фактически собранных бинарей.
5. Сохранять commit, профиль, архитектуру, toolchain, опции, SHA-256 бинарей и архив соответствующих исходников с лицензиями в каждом bundle. Оба бинаря `tinc`/`tincd` должны происходить из одной сборки.

| Профиль | Основные параметры | Владение сетью |
| --- | --- | --- |
| Linux/macOS приложение | `crypto=nolegacy`, `socket_guard=true`, `client_hooks=false` | Go-помощник и socket broker; `DeviceType=fd` |
| Android/TV | То же, cross build NDK | Единственный VpnService, packet adapter и protect/bind broker |
| Windows | То же и `wintun=true` | Go-помощник, физический ifindex и WFP |
| Сервер клиентского слоя | `crypto=nolegacy`, `socket_guard=false`, `client_hooks=true` | Существующий runtime с собственными TUN и `tinc-up` |

В профилях явно отключить ненужные компрессии, интерактивные зависимости, документацию и установку systemd; выбор static linkage закрепить по платформам. Нельзя установить клиентский профиль без hooks на сервер: текущий renderer использует `tinc-up` для интерфейсов и готовности.

Для первого Linux-профиля явно задать `udp_batch_size=1`, `udp_offload=false`, не включать `IffNapi`. В изученном `meson_options.txt` defaults уже равны 32 и true, хотя исторический `REVIEW_FIXES.md` описывает default 1. Опции фиксировать по коду текущего pin. ChaCha SIMD и 64-bit Poly1305 проверять также против scalar-профиля; на неподдерживаемых архитектурах сохранять fallback.

Готовность этапа: все требуемые платформенные бинарные форматы собираются из pin; в клиентской сборке hooks отключены, отсутствие broker/ifindex закрывает доступ; исходники и manifest соответствуют артефакту. Кросс-компиляция Windows/Android считается проверкой сборки, а не работающего VPN.

## Этап 2 Совместимость и перенос Linux в TCP режиме

Точки изменения: тесты `mobile/tincbridge/`, `mobile/clienttinc/`, `test/clienttinc/`, сборка сервера клиентского слоя. Поведение API v1 на первом этапе сохраняется, миграции БД для замены бинаря не планируются.

1. На изолированном стенде проверить четыре сочетания старого и нового native-клиента/сервера: старый→старый, новый→старый, старый→новый, новый→новый. Старый означает точную действующую сборку с патчами, а не чистый upstream.
2. Дополнительно проверить смешанные версии на каждом участке edge/core, включая TCP multihop. Исправления relay на одном endpoint не доказывают правильность промежуточного сервера.
3. Прогнать действующий API → node documents → runtime → системный TUN с настоящими TCP, HTTPS, UDP и DNS; проверить Mux, idle UDP и лимиты физических соединений.
4. Проверить прежний ключ устройства и назначение после обновления. Обычное продление разрешения не должно пересоздавать data path. Смена выхода, истечение, отзыв, блокировка устройства и недоступность API сохраняют действующую семантику.
5. Проверить команды генерации ключа, reload, stop и парсинг `dump connections`/`dump edges`. При недоступной диагностике не выдавать живой процесс за готовое соединение.

Приёмка: работает системный VPN, а не только SOCKS; клиент не видит других устройств, не служит транзитом, не получает доступа к приватным сервисам; учёт не дублируется; отказ входа восстанавливает новые потоки с прежним выходом; отказ выхода даёт назначение в той же стране. Сохранение уже открытого TCP при смене SNAT-пути не обещается.

## Этап 3 Desktop клиенты и жизненный цикл

После Linux подтвердить macOS Apple Silicon и Windows amd64/arm64. На каждой платформе пройти подключение, смену страны, обновление разрешения, потерю входа, сон/пробуждение, смену физической сети, disconnect и аварию native-процесса. Intel macOS добавлять только с отдельной сборкой и проверкой.

Сохранять действующие интеграции: utun framing и PF/DNS на macOS; Wintun/control stop/WFP на Windows; PolicyKit, nftables, маршруты и resolved на Linux. Проверить работу socket guard для `tinc` и `tincd`, в том числе принятого TCP socket и локального control channel. Unix broker использует SCM_RIGHTS version 1 и ACK 0; Windows использует проверенный физический ifindex.

Аварийное завершение привилегированного помощника — самостоятельная проверка. При оставшейся блокировке утечек приложение должно показать восстановление/ошибку и предоставить контролируемую очистку принадлежащих сессии правил. Для macOS эта проблема уже отмечена в текущем документе клиента; замена tinc её автоматически не решает.

Обновление/откат bundle сохраняют ключ и аккаунт, требуют остановки активной сессии и не смешивают старый `tinc` с новым `tincd`. Проверить установку/удаление DEB, macOS bundle и Windows installer на настоящих целевых ОС; подписи и упаковка проверяются отдельно от сетевого пути.

## Этап 4 Android телефон и TV

Точки изменения: `mobile/android/.../QuantwayVpnService.kt`, `PhysicalNetwork.kt`, модели состояния/настройки, `mobile/engine/`, `mobile/tincbridge/`, общая API-логика `mobile/clienttinc/` и Android packaging.

1. Выделить общий платформенно независимый контроллер допуска, назначения и срока доступа из desktop runtime. Передавать тип устройства явно: сейчас `API.Identity` отправляет только `desktop`, а `ValidateConfig` отклоняет `phone`/`tv`. Backend уже принимает три типа; проверить, что они сохраняются и возвращаются без изменения схемы.
2. Добавить отдельный режим Quantway tinc в существующий VpnService и общий lifecycle gate. Режим использует один системный TUN; native tinc получает внутренний packet FD, а пользовательские пакеты проходят через действующий движок с DNS и правилами обхода.
3. Доставлять executables в APK через `nativeLibraryDir`, как в spike. Не исполнять скачанные файлы из writable app home. Сначала ARM64 и x86_64 для тестов; остальные ABI выпускать после отдельных сборок и приёмки.
4. Перенести проверенный двухступенчатый broker: native обращается к приватному файловому Unix socket Go guard, затем descriptor передаётся Java broker для `VpnService.protect` и `Network.bindSocket`. Abstract LocalServerSocket в harness — внутреннее звено, а не замена абсолютного пути `TINC_SOCKET_GUARD`.
5. Привязать все внешние сокеты tinc/API к одному снимку физической Network. При новом network epoch отменять старые операции и пересоздавать внешние сокеты. Отказ protect/bind, отсутствие сети и отказ broker должны закрывать socket без ACK успеха.
6. Телефон получает весь каталог, но держит небольшой активный набор входов. Начальную политику с основным и резервным входом подобрать по измерениям восстановления и расхода батареи; переключение входа не меняет страну/выход. TV и desktop держат полный набор связей. Существующая `Catalog.Connections` задаёт модель, но не реализует мобильный планировщик соединений.
7. Встроить реальные состояния допуска, ожидания входа/выхода, восстановления, истечения и отказа в UI. Страна выбирается отдельно на устройстве; внешние подписки используют прежний режим.

Приёмка на эмуляторе и физическом телефоне: HTTPS и UDP DNS через системный TUN; Wi-Fi↔мобильная сеть; Doze, сон и восстановление; отзыв во время отсутствия API; сохранение ключа; отсутствие DNS/IPv6-утечек; общая политика исключений и отмена параллельных проб. На TV дополнительно проверить постоянные связи и управление с пульта. Успех изолированного spike не заменяет эту приёмку.

## Этап 5 Внешний UDP и производительность

Начинать после TCP-приёмки и подтверждения нового форка на нужных серверных участках клиентского слоя. Переключатель внешнего транспорта ввести в доверенной конфигурации/локальном профиле с TCP как совместимым default; не менять режим глобально по факту появления нового бинаря.

Проверить UDP direct и fallback на TCP, TCP-only вход, NAT rebinding, длительный UDP outage, rekey под нагрузкой, поддельные MAC, replay, дублирование/перестановку, потери и PMTU blackhole. Испытать фактические `IndirectData` и `TunnelServer` настройки нашей сегментированной сети: успешный прямой тест двух daemon не доказывает нужный путь через вход и core.

Отдельно сравнить batch 1/8/32 и offload off/on на Linux amd64/arm64. NAPI/FQ рассматривать только для собственного Linux TUN серверного runtime. Оптимизация `src/linux/device.c` не переносится автоматически на packet FD приложения, Android или utun. Сначала измерить существующий FD-путь, затем решать, нужна ли его переработка.

Измерять полный пользовательский путь с неизменными Xray, Mux, MTU, серверными лимитами и сетью: время первого успешного HTTPS, TCP throughput в обе стороны, UDP loss/jitter, задержку DNS под нагрузкой, CPU/RSS, время восстановления и батарею телефона. Для paced UDP использовать проверенную версию iperf3 3.18 или новее с учётом методики форка; не переносить результаты 3.5 Гбит/с из ARM64 VM на сервис как обещание.

Внутренний VLESS/TLS остаётся TCP-потоком. Внешний UDP снимает только внешний TCP-слой и сам по себе не обеспечивает независимую доставку всех внутренних UDP-потоков. Изменение внутреннего транспорта или Mux — отдельная задача после измерений.

## Этап 6 Выпуск и откат

Последовательность: стенд → отдельный Linux-пилот TCP → обслуживающие его серверы клиентского слоя → desktop → Android телефон → TV → отдельный UDP-пилот. Реальный порядок обновления бинарей приложения и сервера определяется результатом матрицы смешанных версий; при несовместимости нужен изолированный согласованный пилот, а не частичный rolling update.

Перед пилотом зафиксировать измеренный baseline и пороги отказа для задержки/скорости/ресурсов, окно наблюдения и допустимое время восстановления. Отзыв, истечение доступа, изоляция и отсутствие утечек — обязательные условия без допустимой регрессии. При нарушении любого из них выпуск останавливается независимо от прироста скорости.

Сохранять предыдущий проверенный TCP bundle, исходники и checksums. Откат возвращает комплект бинарей и соответствующий профиль транспорта без удаления ключа, перевыпуска устройства, отката БД или замены инфраструктурного mesh. Если смешанные версии не прошли стенд, откат выполнять согласованно для пилотного приложения и его серверных процессов. Старый UDP recovery patch не возвращать как обходной путь нового UDP-режима.

Добавить в безопасную диагностику приложения native commit, профиль сборки, внешний транспорт, сетевой epoch, число активных входов, причину переподключения и последний результат проверки data path. Не передавать ключи, subscription token и полный конфиг. Нативные счётчики ошибок/rekey сначала сделать доступными в структурированной диагностике; изменение общих API и метрик вводить только по необходимости.

Сохранить текущие ресурсные ограничения слоя как исходные условия проверки. Документация развёртывания описывает общий предел 16 активных арендованных устройств и отдельный edge-процесс на устройство/вход. Ускорение криптографии не увеличивает этот предел и не решает масштабирование числа процессов. Расширение ёмкости требует отдельного проекта и нагрузки.

## Набор проверок для реализации

| Уровень | Проверка | Что подтверждает |
| --- | --- | --- |
| Форк | Meson `unit`, `crypto`, `client`, `fork`; scalar/SIMD и sanitizer profiles | Корректность native-кода, rekey, replay, guard, TCP/UDP |
| Профили | Unguarded server и guarded client отдельно | В guarded-сборке часть network/unit suites не регистрируется; один успешный профиль не заменяет оба |
| Go адаптер | `mobile/tincbridge` с race detector и настоящими новыми `tinc`/`tincd` | FD, broker, multihop и lifecycle |
| Сервис | `internal/clienttinc`, `internal/clienttincruntime`, `internal/web`, `internal/store` | Допуск, TTL, документы узлов, отзыв и учёт |
| Полный стенд | `test/clienttinc`, настоящий API/БД, серверные процессы и системные TUN | Путь пользователя, отрицательные проверки и смешанные версии |
| Платформы | Linux VM, macOS, Windows VM, Android device/AVD и TV | Системные маршруты, DNS, kill switch, sleep/network change и установка |

Для фиксации всех перечисленных результатов CI нужен в обоих репозиториях: нативная матрица форка и интеграционная матрица Quantway, всегда с одним полным commit pin. Компиляция и packet-FD smoke тест не считаются подтверждением системного VPN.
