# Архитектура Android клиента и мобильного пробера

Статус: проект архитектуры. Первая платформа — Android. Приложение совмещает универсальный VPN клиент, кабинет Quantway и проверку наших масок из сети пользователя. Первая реализация должна доказать получение задания, реальный запрос через маску, доставку результата и выбор рабочего подключения.

## Границы продукта

Сторонние профили работают без аккаунта Quantway. Наш аккаунт предоставляет баланс дней, паузу, устройства и собственные подключения. Отключение туннеля не приостанавливает подписку. Источник баланса и разрешений — существующий backend.

Локальные проверки помогают подключению. Отправка измерений на сервер включается отдельной настройкой. Чужие профили и их секреты не отправляются в нашу систему наблюдений. Массовый сбор начинается с внутренних и добровольно подключённых устройств.

Мобильный пробер проверяет каждую выданную маску отдельно. Для экспериментов backend может выдавать ещё не опубликованные маски через отдельную группу допуска; публикация в обычной подписке для этого не требуется.

## Компоненты Android

Предлагаемый стек: Kotlin, Jetpack Compose, coroutines и Flow, Room для метаданных и очереди, DataStore для настроек. Ключ шифрования секретов защищается Android Keystore. Версии зависимостей фиксируются при создании проекта.

Первоначально один Android проект с отдельными пакетами, без обязательного Gradle модуля на каждый пакет:

| Компонент | Ответственность |
| --- | --- |
| UI и ViewModel | Подключение, профили, аккаунт, диагностика |
| ProfileRepository | Наши и сторонние подписки, импорт, последняя рабочая конфигурация |
| AccountRepository | Авторизованный API, баланс дней, устройства |
| NetworkMonitor | Физические сети, смена сети, VPN, доступность и тарификация |
| TunnelController | Состояние соединения, запуск и остановка VpnService |
| ProbeCoordinator | Выбор заданий, бюджет, отмена, локальные результаты |
| ReportOutbox | Надёжная доставка пачек и повторная отправка |
| EngineBridge | Узкий интерфейс к Go ядру через AAR |

VpnService обслуживает пользовательский TUN интерфейс. ProbeCoordinator использует отдельные исходящие соединения ядра и не поднимает второй системный VPN. UI не владеет временем жизни туннеля.

Состояния туннеля: disconnected, preparing, connecting, connected, reconnecting, stopping, error. Состояния прогона: queued, running, completed, cancelled, deferred. Смена сети отменяет текущий прогон; его остаток не превращается в ошибки маршрутов.

Для передачи всего трафика телефона нужен отдельный адаптер TUN к движку. `xrayfetch` решает только задачу проверочных запросов и не заменяет этот адаптер. Выбор реализации TUN, UDP и DNS — обязательная часть технического прототипа, с проверкой лицензий и совместимости.

| Существующий код | Решение |
| --- | --- |
| `internal/probe/jobs.go` | Сохранить сборку заданий по маршруту и каждому входу; выделить общую сборку с передаваемой identity и фильтром допуска |
| `internal/probe/xraydialer.go` и `stream.go` | Использовать ту же сборку исходящих, документы протоколов и served имена |
| `internal/xrayfetch` | Переиспользовать выполнение реального запроса через отдельный экземпляр Xray |
| `internal/beacon/wire` | Сохранить смысл route_id, inbound_id, kind, outcome, rtt; мобильный контракт оформить отдельно |
| `internal/beacon/record.go` | Выделить общую валидацию пар и исходов; мобильные отчёты писать отдельно |
| `internal/probe/tally.go` | Сохранить серверный свод; чистые правила свежести и последовательностей можно применять к мобильным срезам |
| `internal/probe/coalesce.go` | Переиспользовать принцип объединения пересчётов, чтобы каждый телефон не запускал полный свод |
| `internal/beaconagent` | Переиспользовать отдельные алгоритмы; Linux обнаружение модемов, IMEI, интерфейсы и самообновление не переносить |
| `internal/device`, `internal/subs` | Сохранить модель устройств, отзыва доступа, баланса дней и паузы |

Не отдавать телефону результат BuildJobs с общей `ProbeClientID`: существующие задания содержат привилегированную identity пробера. Общим должен стать построитель исходящего, принимающий отдельную разрешённую identity.

Go библиотека находится в `mobile/engine` в отдельном модуле с тем же префиксом репозитория, что позволяет импортировать `internal/xrayfetch` и изолировать зависимости gomobile от backend. Обёртка экспортирует простые gomobile совместимые типы и функции StartProbe, CancelProbe, Capabilities, EngineVersion; результаты передаются JSON или байтами. Внешние вызовы не принимают типы pgx, topology или Xray.

Пробер и основной туннель используют одну закреплённую версию Xray и одинаковую регистрацию транспортов. Мобильная сборка проверяется отдельно: отсутствие pgx в xrayfetch ещё не доказывает совместимость всех зависимостей с Android.

## Привязка проверок к сети

NetworkMonitor выбирает доступную физическую Network. Все внешние сокеты движка, включая UDP и DNS, должны пройти Android адаптер: исключение из собственного VPN через protect и привязку к выбранной Network. Одного protect недостаточно для выбора Wi-Fi или мобильной сети.

Общий Go код получает платформенный callback для подготовки сокета до connect. Нужно исследовать точки подключения callback в закреплённой версии Xray; готовой мобильной реализации в текущем xrayfetch нет. Для имени входа используется DNS выбранной сети; TLS и Reality сохраняют исходное имя. Привязка всего процесса к сети нежелательна: туннель, API и пробер могут иметь разные политики.

Критерий корректности — проверка действительно выходит через выбранную физическую сеть, даже когда включён наш туннель. Проверяется на стенде по наблюдаемому выходу и маршруту, включая DNS и UDP.

При чужом активном VPN или системном запрете обхода VPN проверка может быть невозможна. В этом случае возвращается deferred с причиной; результат не маркируется как измерение исходной сети. Для первой версии такие режимы можно полностью исключить из коллективной статистики.

Network epoch — случайный локальный идентификатор текущего подключения. Он меняется при переподключении и не является SSID, IMEI или постоянным отпечатком сети. Если epoch изменился во время задания, измерение отменяется.

## Мобильный API

Предлагаемые новые маршруты, которые пока не реализованы:

| Метод и путь | Назначение |
| --- | --- |
| POST /api/mobile/v1/enrollments/exchange | Обмен одноразового разрешения привязки на мобильную сессию |
| POST /api/mobile/v1/session/refresh | Обновление сессии с ротацией refresh токена |
| GET /api/mobile/v1/account | Наш баланс, состояние и привязанное устройство |
| POST /api/mobile/v1/probe/runs | Запрос небольшого набора заданий с capabilities и контекстом сети |
| POST /api/mobile/v1/probe/reports | Идемпотентная отправка результатов |

Привязка создаётся в авторизованном кабинете или боте и расходуется один раз. При обмене backend проверяет лимит устройств. Ссылка /sub не даёт прав кабинета. Точные операции входа нужно согласовать с существующей авторизацией портала при реализации.

Access токен короткоживущий; refresh токен связан с установкой и устройством. Установка получает отдельное разрешение probe:submit, а не токен инфраструктурного маяка. Отзыв устройства прекращает обновление сессии и получение заданий.

Запрос прогона содержит capabilities, версии приложения и ядра, transport сети, metered, roaming и network_epoch. MCC/MNC передаётся только если доступен и разрешён; неизвестный оператор остаётся неизвестным. Оператор SIM не считается достоверным оператором доступа при роуминге. Регион и ASN при необходимости определяет backend, отмечая источник; IP запросов через VPN не описывает исходную сеть.

Ответ прогона содержит run_id, expires_at, config_revision, interval_hint, бюджет и задания. Задание содержит job_id, route_id, inbound_id, kind, fingerprint конфигурации, формат и версию engine payload, готовое исходящее, ожидаемый ответ контрольного адреса и таймаут. Сервер сохраняет выданный набор и проверяет отчёты по нему.

Для первой внутренней версии допустимо использовать существующий protobuf OutboundHandlerConfig в base64, если закреплена совместимая версия ядра. Этот внутренний формат не становится бессрочным публичным контрактом: capability negotiation исключает несовместимые задания, обновление ядра сопровождается тестами совместимости. Декодирование protobuf остаётся в Go.

Задания используют credentials конкретного устройства для разрешённых опубликованных маршрутов. Экспериментальным маскам нужны отдельно выдаваемые, ограниченные и отзываемые тестовые identity с серверным учётом provisioning. Поле expires_at само по себе не отзывает Xray credential. До появления такого механизма мобильным клиентам не выдаются скрытые маски вне прав подписки.

Отчёт содержит report_id, run_id и результаты по job_id: outcome, reason_code, elapsed_ms, измеренные байты, время измерения и network_epoch. RTT в старом контракте и полное время HTTP запроса различаются по смыслу: мобильный elapsed_ms не называется сетевым RTT. Версии и revision фиксируются на прогоне.

Исходы: ok, fail, unprobeable, cancelled, no_network. Только первые два являются наблюдением доступности, если подтверждена исходная сеть. Смена сети, ошибка сборки движка, отсутствие разрешений и остановка приложения не считаются отказом маски. Общая недоступность контрольного адреса выделяется как неопределённый результат с повтором через резервный адрес.

Сервер валидирует владельца run, срок, fingerprint, допустимые пары, границы времён и размеров. Повтор report_id возвращает прежний ответ без повторного изменения статистики. Уникальность результата по run_id и job_id защищает от копий в разных пачках. Для частичных отчётов сервер возвращает принятые job_id; очередь удаляет только подтверждённые элементы. Повтор с тем же ID и другим телом отвергается.

Загрузка заданий требует доступного API. При блокировке API допустим локальный подбор по сохранённым действующим профилям; отправка отчёта откладывается. Истёкшие экспериментальные credentials не используются. Резервные адреса управления задаются доверенной конфигурацией приложения.

## Хранение и свод результатов

Предлагаемые таблицы: mobile_installations, mobile_probe_runs, mobile_probe_jobs, mobile_probe_reports, mobile_probe_observations и mobile_probe_health. Задания привязаны к конкретным версиям и identity. Секретный payload хранится только необходимое время и не попадает в журнал консоли.

Наблюдения содержат установку, маршрут, вход, revision, epoch, сетевой контекст, версии, исход, причину и время приёма сервером. Время клиента служит дополнительным полем; свежесть не доверяет часам телефона без проверки. Начальная политика хранения: сырые результаты 14 дней, сводные срезы 90 дней; сроки конфигурируемые. Удаление установки отзывает credentials и очищает её персональную привязку.

Мобильные наблюдения не пишутся напрямую в route_beacon_health и route_pool_beacon_health. Действующий Tally ориентирован на доверенные маяки, а телефон может исчезнуть, сменить сеть или прислать неверные данные. Серверный health и гейты раскатки остаются на существующих маяках.

Локальный выбор использует свежие результаты этой сети. Серверные рекомендации учитывают отдельные срезы по сети, оператору, версии конфигурации и ядра. Один телефон не может скрыть маршрут для всех. Порог коллективной рекомендации определяется после пилота; несколько установок одного аккаунта не считаются полностью независимыми наблюдателями.

В консоли нужны отдельные поля: состояние доверенных маяков, успешность мобильных проверок, число независимых участников, свежесть, разбивка по сети и версии, ошибки клиента. Это позволяет различить отказ инфраструктуры, ограничение сети и регрессию приложения.

## Планирование и расход ресурсов

Первые триггеры: ручная диагностика, подключение без свежего результата, сбой текущего соединения и смена сети во время активного использования. В MVP пробер не гарантирует круглосуточную работу после закрытия приложения.

Предлагаемые начальные лимиты пилота: до 6 заданий в прогоне, 2 параллельно, до 8 секунд на задание, до 30 секунд на прогон, до 256 КиБ суммарного прикладного трафика. Это настройки эксперимента; лимит прикладных байтов не равен полному расходу с накладными расходами транспортов. Ответ и запрос имеют отдельные ограничения размера; доступный FetchThrough нужно дополнить проверкой лимита чтения и отменой по бюджету.

При успешном подборе локальный прогон завершается; дополнительные экспериментальные задания исполняются только в разрешённом режиме участия. Маски распределяются между устройствами с учётом недостаточного покрытия, чтобы не проверять весь каталог каждым телефоном.

WorkManager обслуживает доставку очереди и редкие разрешённые фоновые задания. Он не заменяет постоянный цикл маяка: периодические задачи имеют минимум 15 минут и могут задерживаться системой. Частые проверки выполняются при активном приложении или работающем VPN сервисе в пределах разрешённого жизненного цикла.

## Этапы реализации и критерии готовности

1. Собрать Android AAR с существующими xrayfetch и awgprobe. Проверить Reality, XHTTP и AmneziaWG без системного TUN, отмену, очистку ресурсов, отсутствие прямого fallback при ошибке.
2. Реализовать платформенный socket callback. Доказать исходную сеть проверок при включённом собственном VPN; проверить Wi-Fi, cellular, UDP, DNS, IPv6 и смену сети на реальном телефоне.
3. Добавить внутреннюю привязку устройства, выдачу runs и приём reports. Проверить повтор пачки, отзыв устройства, истечение задания, подмену job_id и несовместимость ядра.
4. Добавить outbox и локальный выбор. Проверить перезапуск процесса между измерением и отправкой, отсутствие API, сохранение последней рабочей конфигурации.
5. Подключить TUN адаптер, основной экран, профиль нашего сервиса и импорт сторонней VLESS подписки. Проверить восстановление сети и сохранение баланса дней на backend.
6. Показать мобильные наблюдения в консоли отдельно от серверного health. Провести пилот, измерить батарею и трафик, затем расширять протоколы и планирование.

Автотесты проверяют значимые границы: отсутствие повторного учёта, изоляцию прав, свежесть revision и network epoch, реальные запросы через тестовые Reality и XHTTP серверы. Эмулятор подходит для UI и интеграции API; работа в сетях операторов и расход батареи требуют физического Android устройства.

## Поддержка AmneziaWG в первой версии

AmneziaWG входит в обязательный объём первой версии: подключение из нашей подписки, локальная проверка, автоматический выбор и мобильные отчёты. В текущем backend формат incy сохраняет ссылки awg:// с конфигурацией в base64url, Clash формирует amnezia-wg-option; форматы base64, Happ и singbox исключают AWG. Использование обычного base64 формата нашим клиентом потеряет этот протокол.

Для прототипа клиент может явно запросить format=incy и разобрать смешанный список VLESS и AWG. Для стабильного приложения нужен собственный capability aware формат с типизированными профилями, идентификаторами маршрута и входа, revision и конфигурацией нужного движка. Общими остаются Selector, BuildAWGConf и ParseAWGLink; отдельная выдача не создаёт вторую модель подписок.

EngineBridge маршрутизирует задания в два движка: Xray через internal/xrayfetch и AmneziaWG через internal/awgprobe. Последний уже использует amneziawg-go/v3 и netstack без системного TUN и root, выполняет handshake, затем HTTP запрос через туннель. Он предусматривает Options.Listen и Options.Resolve — точки интеграции Android UDP сокета и DNS выбранной сети. Мобильную сборку и отмену операций необходимо проверить экспериментально.

Контракт задания содержит engine=xray либо engine=amneziawg и kind=awg для AWG проверки. Вместо protobuf Xray передаётся отдельная AWG конфигурация конкретного проверяющего. Версия схемы AWG и поддерживаемые параметры обфускации входят в capabilities; неизвестные обязательные параметры дают unprobeable, а не упрощённый WireGuard. Пользовательские параметры конфигурации сохраняются без потери.

Один AWG peer нельзя одновременно использовать основным туннелем и независимым пробером: изменение endpoint может нарушить активное соединение. При активном AWG подключении проверка этого же профиля выполняется через существующий туннель и помечается как наблюдение активного подключения. Независимые параллельные пробы требуют отдельных зарегистрированных peer, как текущие пробы модемов. Для фоновых тестов других AWG профилей также выдаются отдельные peer; их создание, доставка на узлы и отзыв используют существующий provisioning.

Результат различает ошибку конфигурации, отсутствие provisioning пира, отсутствие handshake и ошибку HTTP после handshake. Пока peer не подтверждён на узле, отказ не считается доказательством блокировки сети. Подробности handshake возвращаются как необязательные диагностические поля; существующий awgprobe потребует расширения результата, если нужны отдельные времена этапов.

Полноценный AWG туннель телефона использует Android VpnService с AWG адаптером; netstack зонда не заменяет этот адаптер. В одном активном системном VPN выбран один движок. Переход Xray ↔ AWG управляется TunnelController с явным восстановлением DNS и маршрутов. В первую приёмку включаются AWG импорт, прохождение трафика, проба при работающем Xray, отсутствие конфликта peer при активном AWG и смена физической сети.

## Среда разработки

Среда реализации: Apple M3 Pro, Parallels Desktop 27.0.3, одна выключенная VM Ubuntu Linux. Установлены JDK 17, Android SDK 35, NDK 28 и ARM64 Android Emulator. Диагностическое приложение собрано и запущено напрямую на macOS в AVD Quantway_API_35 с аппаратным ускорением Hypervisor.Framework.

Основной предлагаемый путь — ARM64 Android Emulator непосредственно на macOS. Запуск внутри Ubuntu в Parallels требует отдельной проверки доступности nested virtualization и KVM, совместимого образа и ускорения; установленный Parallels сам по себе этого не подтверждает.

## Реализованный Android пилот

`mobile/android` содержит клиент с системным VPN, `mobile/engine` — AAR с Xray и AmneziaWG и адаптерами TUN. Ручки profiles, runs и reports подключаются флагом MOBILE_PROBE_ENABLED=1. Миграции 0120–0122 хранят метаданные прогонов, отчёты и независимые AWG peer пробера. Backend проверяет выданные job_id, владельца, epoch, срок, повтор report_id и ограничение частоты.

Клиент принимает одну полную ссылку подписки. Пилот авторизуется существующим токеном устройства без прав управления аккаунтом. Профили и задания ограничены текущей подпиской. AWG пробы используют отдельный peer и адрес; его доступ исключается при блокировке, отзыве или неактивной подписке. Системный VPN и пробы могут работать одновременно; сокеты пробера привязаны к физической сети и защищены от попадания в собственный туннель.

При смене сети текущие измерения прерываются, после стабилизации сети проверка автоматически продолжается с новым прогоном. VPN восстанавливается на новой сети, проверяет доступность и перебирает доступные профили при отказе. Отчёты сохраняются атомарно перед отправкой; очередь разделена по origin и отпечатку токена. В версии 0.3.0 ссылки и кеш профилей хранятся в закрытом noBackup каталоге, зашифрованными AES-GCM с ключом Android Keystore. Кабинет открывается во встроенном браузере с существующим входом. Консоль показывает отдельные агрегаты мобильных наблюдений за 24 часа. В 0.3.0 реализован импорт сторонних URI/Base64 подписок VLESS, HY2 и AWG. Отдельная мобильная сессия, WorkManager и mesh остаются следующими этапами.

## Клиентский слой tinc — новый проект от 31.10.2026

Прежняя идея IPv6 mesh с транзитом через телефоны заменена [отдельной спецификацией клиентского tinc-слоя](2026-10-31-client-tinc-layer-design.md) и [планом реализации](../plans/2026-10-31-client-tinc-layer.md). Начат изолированный технический прототип; режим ещё не подключён к приложению. Проверенные части и ограничения перечислены в [отчёте этапа 0](../../audits/2026-10-31-client-tinc-stage0.md).

Приложение получает все наши входы нового слоя. ПК и ТВ держат постоянные связи со всеми входами, телефоны динамически управляют активным набором. Пользователь отдельно на каждом устройстве выбирает страну; система назначает выход и при его отказе автоматически выбирает другой в той же стране. До выхода трафик идёт через серверный меш. Транзит выполняют только наши серверы.

Это самостоятельный режим рядом с текущими VPN-подключениями, с собственным TCP/UDP-транспортом tinc. Публичный IPv6 на клиенте не требуется; служебный qmesh и его права приложениям не выдаются. Механизм индивидуального выхода, изоляция устройств и платформенные адаптеры проходят отдельный технический прототип по новой спецификации.

## Списки обхода VPN в Android — реализовано в 0.3.0

Политика приходит из существующих списков internal/lists вместе с профилями. Xray применяет её к собственным исходящим и к AWG netstack; личные доменные исключения имеют первый приоритет.

Переиспользуются списки internal/lists и порядок internal/subfmt/split.go: принудительный tunnel по домену имеет приоритет перед direct по домену и GeoIP. Private, category-ru, whitelist и сети ru идут напрямую. Внутренний префикс mesh имеет отдельный приоритет выше private, чтобы не уйти напрямую. Политика применяется и к Xray, и к AWG.
