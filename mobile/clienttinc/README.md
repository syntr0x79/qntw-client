# Отдельный Linux-прототип клиентского tinc

Прототип работает отдельно от текущего Linux-интерфейса Quantway и его движка.
Его первый запуск выполняется в изолированном network namespace или отдельной
тестовой VM: основной интерфейс и соединение соседней сессии трогать не нужно.

## Что входит

`quantway-tinc` — foreground CLI с общим Xray, закреплённым в `mobile/go.mod`.
Рядом лежат native `tincd` и `tinc` с обязательной подготовкой внешних сокетов и
проверенным TCP relay patch. Пользовательский IPv4 TCP/UDP идёт через отдельный
системный TUN → VLESS/TLS до назначенного выхода → overlay TUN → tinc-входы.
Сертификат выхода и TLS name приходят по авторизованному HTTPS API; системные
корни для внутреннего listener отключены. `allowInsecure` не используется.

Linux-прототип использует внешний транспорт tinc только поверх TCP
(`TCPOnly = yes`, клиентские `PingInterval` и `PingTimeout` — 15 секунд).
Смешанный UDP/TCP-режим пока отключён: в изолированном NAT-тесте он воспроизвёл
рассинхронизацию SPTPS. Пользовательские UDP и DNS по-прежнему переносятся внутренним
VLESS/TLS-туннелем. При потерях или большой нагрузке внешний TCP задерживает другие
потоки; низкая задержка UDP в этом режиме не гарантируется. Шифрование и защита от
повторных пакетов сохранены.

Готовность нового пути проверяется локально с повтором через 500 мс:
аутентифицированный вход и, когда задан HealthURL, успешный запрос через
назначенный выход. Эти повторы не запрашивают конфигурацию повторно и не
продлевают доступ. После успеха частые проверки прекращаются; при обычном
обновлении конфигурации выполняется прежняя проверка. Интервал API остаётся
15 секунд, срок доступа и десятисекундный предел HTTP health-check сохранены.
Stop отменяет проверку, а истечение доступа закрывает путь перед публикацией
состояния. Серверный период получения настроек этой оптимизацией не меняется.

Обычные потоки Xray объединяются через Mux с параллельностью 8: несколько
DNS-ассоциаций делят одно TLS-соединение к выходу. Серверный предел 64 физических
соединений устройства сохранён. Постоянное
возобновление XUDP по GlobalID отключено в контексте каждого клиентского Xray:
UDP-потоки принадлежат своему назначению и его UUID. Пользовательские UDP/443
разрешены; проверка TLS, серверные запреты внутренних адресов, отзыв и учёт
сохраняются.

Локальные UDP-ассоциации TUN завершаются после 10 секунд простоя для DNS/53
или 60 секунд для остального UDP. Таймер обновляется полезными данными в обоих
направлениях; активные DNS и UDP не обрываются по общему времени жизни. Если тот
же источник начинает отправлять обычный UDP вместо DNS, его ассоциация получает
более длинный таймер. Следующий пакет после простоя создаёт новую ассоциацию.
Эта политика использует публичный обработчик Xray и не меняет зависимость,
таймеры TCP, TLS или серверные лимиты.

У каждого устройства собственный ключ; серверный core-граф ему не выдаётся.
Приложение держит метасоединения со всеми входами из документа. Backend выбирает
узел в указанной стране. Прототип обновляет документ с интервалом до 15 секунд
(чаще перед истечением короткого разрешения), сохраняет
неизменённый data path при продлении и перестраивает его при смене назначения.

## Сборка

```sh
mobile/scripts/build-tinc-linux.sh arm64
mobile/scripts/build-tinc-linux.sh amd64
```

Архивы находятся в `bin/quantway-tinc-linux/`. Нужны Go, Docker и право сборки
Linux-контейнеров. Скрипт передаёт Docker только маленький native source context;
credentials и весь checkout в образ не копируются.

На Linux нужны root, `/dev/net/tun`, `ip`, `nft` и `resolvectl` для системного
режима. Непосредственный запуск меняет сеть текущего namespace — для первого
теста используйте отдельный namespace с собственным исходящим соединением.

## Приватная конфигурация

Создайте `device.json` с правами `0600` в приватном каталоге. Формат:

```json
{"origin":"https://qntw.link","token":"DEVICE_SUBSCRIPTION_TOKEN"}
```

Секрет передаётся только через файл. Он не выводится в status, логи, аргументы
процессов или сообщения ошибок. Доступ backend определяется действующей подпиской,
тарифом и возможным запретом устройства. Прототип не создаёт аккаунты и подписки.

## Подключение и управление

Из распакованного каталога, внутри выделенного тестового namespace:

```sh
./quantway-tinc connect --config /private/device.json --state /private/tinc-state --country PL
```

Процесс остаётся в foreground. Отдельные команды в том же namespace:

```sh
./quantway-tinc status --state /private/tinc-state
./quantway-tinc country --state /private/tinc-state --country SE
./quantway-tinc check
./quantway-tinc stop --state /private/tinc-state
```

Управление проходит по Unix socket в приватном state directory (`0700`), а не
по публичному порту. `--socks-only` поднимает overlay и локальный SOCKS
`127.0.0.1:1089` без системного TUN/DNS. Это отдельный диагностический режим,
а не доказательство системного VPN.

В примерах используются PL и SE из подготовленного пилота. Выбирать можно
только страны включённого оператором каталога и доступные текущей подписке;
наличие двухбуквенного кода само по себе не добавляет страну или выход.

Для namespace-теста без systemd-resolved есть `--dns none`; тогда DNS системы
не меняется, а UDP/DNS проверяют явно через разрешённый выход. Обычный режим
использует `resolvectl` для TUN и откатывает его при остановке. Прототип пока
не переносит доменные исключения интерфейса: весь пользовательский IPv4 идёт
в VPN, пользовательский IPv6 блокируется. Это отдельный полный VPN-режим.

## Отказ и очистка

Физические tinc/API sockets помечены SO_MARK и привязаны к исходному интерфейсу.
Для них создаётся отдельная physical routing table. Внутренний listener выхода
маршрутизируется только через overlay. На пользовательском TUN устанавливаются
split default routes; nft разрешает только VPN, его control transport и loopback.
DNS для API использует отдельный marked resolver: адрес исходного uplink DNS
считывается до установки VPN из systemd-resolved или resolv.conf; при отсутствии
нелокального resolver используется control-only адрес 1.1.1.1. DNS пользовательских
приложений не получает этот физический обход.

Недоступный API не продлевает предыдущее разрешение. При истечении или отзыве
останавливаются native tinc и внутренний Xray, но системный TUN и блокирующий
фильтр остаются до явного stop/SIGTERM. Это предотвращает незаметный переход
пользовательского трафика в обычный интернет. При остановке возвращаются DNS,
маршруты и правила текущего namespace.

В случае SIGKILL filter намеренно может остаться. Не удаляйте его автоматически
в пользовательской сессии. Для теста проще удалить целиком выделенный network
namespace. Production crash recovery, смена физической сети и непривилегированный
помощник интерфейса требуют отдельного этапа; соседний UI сейчас не подключён.

## Сквозная проверка

Опциональный `go test -tags clienttinc_stand ./test/clienttinc` из корня
репозитория создаёт отдельную локальную тестовую БД и Docker network namespaces.
Он запускает настоящий backend API, шесть настоящих серверных агентов и два
клиента с системным TUN; проверяет TCP/UDP, страны, отказ выхода, отзыв, истечение
разрешения, защиту внутренних сервисов, учёт и очистку. Нужны предварительно
собранные клиентский/серверный bundles и локальная тестовая PostgreSQL.

Проверка не использует поддельные ответы identity/country/config и не подключается
к production. Существующие правила DROP, обычный тестовый сервис и настройки
глобального/физического forwarding сохраняются и проверяются отдельно.

Проверка TCP-режима 2026-10-31:

- `test/clienttinc/native_transport.py` воспроизвёл в смешанном режиме ошибки
  `Invalid packet seqno`, `Handshake phase not finished yet` и перезапуски SPTPS
  через NAT с задержкой, потерями, дублированием и перестановкой пакетов.
- При `TCPOnly = yes` и клиентских таймерах 15/15 тот же TCP-поток передавал
  2730 порций данных в течение 190,02 секунды без ошибок SPTPS. UDP прошёл
  60/60 проверок до нагрузки и 90/90 после восстановления. При одновременной
  интенсивной TCP-передаче часть UDP-ответов не уложилась в 300 мс.
- Полная проверка с настоящими API, системным TUN и двумя клиентами прошла
  46 проверок за 117,05 секунды, включая UDP/DNS, отзыв, изоляцию, учёт и очистку.
  Она использовала TCP-режим с эффективным клиентским таймаутом 5 секунд;
  окончательные 15/15 отдельно проверены нативным NAT-тестом выше и тестом renderer.

Проверка браузерной нагрузки с настоящим API и системным TUN воспроизвела
исходную ошибку: 100 разных UDP/DNS-источников заняли ровно 64 физических
соединения; ответили 63 DNS-запроса, а все 16 новых TLS-потоков отказали.
При Mux тот же сценарий ответил 100/100 и 16/16, использовав 19 соединений
после предшествующей нагрузки. Полный прогон с 512 МиБ проверенных TLS-данных,
запретами частных адресов/доменов, IPv6, сменой страны, отзывом и учётом прошёл
49 проверок за 158,82 секунды. Отдельный тест настоящих TLS/VLESS/Mux-кадров
проверяет нулевой UDP GlobalID и положительный контроль штатного Xray с ненулевым
ID. Независимый серверный guard-тест закрывает общий транспорт двух подпотоков
при смене UUID или отзыве, сохраняя другое устройство.

Длительный DNS-churn обнаружил отдельную проблему: без локального завершения
ассоциаций обычный Mux лишь переносил порог отказа примерно с 64 до 512 источников.
Исходный Mux при 20 новых источниках в секунду ответил на 511 из 1024 запросов,
занял все 64 соединения и отказал всем 16 новым TLS-потокам. С политикой простоя
ответили 1024/1024 без повторов и 16/16 TLS при 24 соединениях. Положительный тест
использует DNS-таймаут 1 секунду: прежний искусственный предел 150 мс смешивал
TCP head-of-line задержку с исчерпанием ресурсов. Низкая задержка UDP не заявляется.

Итоговая приёмка политики простоя: 50 сквозных проверок за 254,15 секунды плюс
сверка учёта в БД, 512 МиБ проверенных TLS-данных, активные DNS и обычный UDP
дольше 76 секунд, повторное использование source port после простоя и переход
DNS к обычному UDP. При аварии только native tinc и восстановлении с тем же UUID
обработчик закрывает старые логические UDP-потоки. Пустые физические Mux-пулы
освобождаются отложенно: все 15 старых соединений исчезли к 30,20 секунды в
изолированной проверке. Явный stop с завершением помощника освободил все
дескрипторы за 0,108 секунды. Немедленное закрытие физического пула внутри
живого процесса и устойчивость к неограниченной серии аварий не заявляются.

Помощник ARM64 `35b3d6db…` установлен на тестовую Ubuntu VM. Пользователь
подтвердил пять минут стабильного просмотра сайтов после установки. Пассивное
наблюдение показало неизменный процесс, два входа и число физических соединений
ниже прежнего предела 64. Это ограниченная проверка одного окружения.

## Автоматический допуск

При `CLIENT_TINC_OPEN_ENROLLMENT=true` каталог доступен всем активным устройствам с оплаченной подпиской, без ручного allowlist. Регистрация ключа не занимает сетевое место. Место выделяется при подключении; общий предел — 16 одновременных устройств. Ответ `capacity_exhausted` обрабатывается до создания TUN и блокировки сети. Явный административный запрет устройства имеет приоритет.
