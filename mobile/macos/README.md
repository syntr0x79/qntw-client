# Quantway для macOS

Основное приложение Apple Silicon версии 0.3.2 находится в `bin/quantway-macos-client/Quantway.app`; рядом — ZIP, контрольная сумма и результат интеграции. В основной пакет включены проверенные tinc и исправленный Xray. Это клиент AppKit/WebKit с локальными ресурсами интерфейса, общими Go-компонентами Linux/Windows и отдельным привилегированным сетевым процессом macOS.

Интерфейс 0.3.0 перенесён из «Quantway — концепт приложения2.html»: четыре базовых экрана, главная со состояниями подключения, страны и панель Tinc, семь вкладок кабинета, формы и диалоги по карточкам состояний. Сохранены Manrope, палитра, иконки и размеры компонентов. Полный каталог и пассивные шаблоны — в `Design/`; происхождение — в `DESIGN-SOURCE.json`. Примеры и демонстрационные таймеры не управляют рабочим VPN.

[Статус для дизайнера](../../docs/design/2026-11-03-quantway-desktop-missing-design.md) обновлён: полученные экраны закрыты, оставшиеся продуктовые решения и ограничения API перечислены отдельно. Все действия кабинета имеют видимые точки входа; системное меню сохранено. Закрытие окна с активным VPN позволяет оставить приложение в строке меню, а выход ждёт завершения сетевого помощника.

## Возможности

- Вход по коду, восстановление сессии и привязки этого Mac, замена устройства при заполненном лимите. Cookie остаётся в нативном процессе и системной связке ключей.
- Подписки Quantway и несколько внешних подписок с локальным сохранением в связке ключей; их конфигурации не отправляются в API кабинета.
- Общий с Linux/Android парсер и проверка маршрутов; поиск, фильтр доступности и выбор рабочего маршрута. Длительность проверки подписана отдельно от живого ping.
- Обычный VPN через Xray/AmneziaWG и `utun`, с настройкой адресов из AWG-конфигурации.
- Tinc через комплектные `tinc`/`tincd`, исходный механизм серверного допуска, регистрации ключа, назначения страны, обновления разрешения, истечения и переподключения. Ключ этого устройства хранится у root отдельно от ссылки подписки.
- Реальные наблюдения соединений со входами Tinc и счётчики принадлежащего сессии интерфейса. Состояние «Подключено» требует проверки назначенного туннеля, системного маршрута, HTTPS и UDP DNS через системный TUN, а также выбора DNS в macOS.
- Кабинет: подписка, устройства, ссылки и QR, блокировка/перевыпуск/удаление, дополнительное место, тарифы и счета, промокод, пауза, история, приглашение, Telegram-прокси и привязка, обновление кода входа, присоединение покупки, поддержка с изображениями.

Наличие клиентского действия не заменяет проверку серверного разрешения: роли, тарифы и доступность определяются существующим API. Диалоги используют компоненты нового макета. Автоматическое восстановление после аварийной гибели root-процесса и отправка аварийного отчёта пока не реализованы; их успешные состояния не имитируются. Тема обращения и пакетная отправка галереи ограничены контрактом API.

## Сетевой процесс

Приложение запускается обычным пользователем. При явном подключении системный запрос macOS разрешает ровно один сетевой процесс. Установка постоянного root-сервиса не требуется. Учётные данные передаются по приватному Unix-соединению с проверкой UID ядром; в командную строку, AppleScript и временные файлы они не попадают. Оба режима используют общую системную блокировку.

Сетевой слой использует динамический `utun`, привязку транспортных сокетов к физическому интерфейсу и scoped host routes для проверенных адресов API/входов, отдельные IPv4/IPv6 split-маршруты, временный DNS в SystemConfiguration и собственный PF anchor внутри системного `com.apple/*`. Его исходящие разрешения проверяются на каждом пакете (`no state`): включение после готового handshake не реконструирует TCP-состояние без параметров исходного SYN. Глобальные правила PF и постоянные DNS-настройки пользователя не заменяются. В текущем PF-режиме привилегированные IPv4 TCP/UDP-транспорты на физическом интерфейсе разрешены, кроме обычного DNS на порту 53; обычные приложения ограничены туннелем. Это не изоляция от другого root-процесса. Адреса фиксированного API Quantway разрешаются до активации туннеля; затем служебный HTTP-транспорт использует сохранённые адреса с привязкой сокетов к физическому интерфейсу и обычной проверкой TLS. Новых внешних DNS-запросов для API во время сессии не требуется.

Tinc использует пакетный FD с преобразованием четырёхбайтового заголовка `utun`, отдельный overlay, назначенный сервером внутренний VLESS/TLS и строгий владелец сокетов. Собственный диспетчер Tinc устанавливается только при запуске этого режима в отдельном процессе; он не использует глобальную физическую сеть обычного VPN. Нативные script hooks отключены при сборке. Смена режима и источника выполняется после явного завершения предыдущего соединения.

Перед глобальным переключением маршрутов, DNS и PF клиент подтверждает передачу HTTPS через Tinc. Ожидание входа или выхода оставляет обычный интернет включённым. Стартовая попытка ограничена 45 секундами; по тайм-ауту сессия завершается. После подключения готовность повторно проверяется через системные HTTPS и DNS; подтверждённая ошибка завершает сессию и запускает очистку. Истечение или отзыв самого разрешения сохраняют описанное ниже блокирование до явного отключения.

По истечении разрешения Tinc передача останавливается, а системный туннель и фильтр сохраняются до отключения. EOF от приложения отменяет сессию. Штатное отключение удаляет принадлежащие сессии маршруты, DNS и фильтр; ошибка очистки возвращается приложению и не выдаётся за успех. Аварийное завершение самого root-процесса и восстановление сети после него требуют отдельной системной приёмки; эту сборку нельзя считать прошедшей такую проверку по одному факту компиляции.

## Сборка

Нужны macOS ARM64, полный Xcode, Go из `mobile/go.mod`, Meson и Ninja из `mobile/native/tinc/source-pin.env`. Исправленный Xray закреплён обычным Go module replace; общий кэш Go не изменяется. Native-сборка использует закреплённый commit нашего форка; старые патчи повторно не применяются. Сборка не подключает VPN и не меняет системную сеть.

```sh
# При отсутствии библиотеки парсера:
./mobile/scripts/build-engine-macos.sh

# Нативный форк с обязательным guard и отключёнными hooks:
TINC_SOURCE_REPOSITORY=/path/to/tinc-fork ./mobile/scripts/build-client-tinc.sh host

# Упаковать готовую проверенную пару из host-Darwin-arm64-fork:
./mobile/scripts/build-macos-client.sh
```

`QUANTWAY_MACOS_BUILD_DIR` и `QUANTWAY_MACOS_OUTPUT_DIR` задают каталоги промежуточных файлов и результата; `QUANTWAY_MACOS_TINC_DIR` — готовый native bundle. Сборщик проверяет commit, профиль, архитектуру target и SHA-256 всех native-артефактов, собирает помощники и интерфейс, включает архив соответствующих исходников и лицензию. В `.app` сохраняются manifest native-сборки, исходные checksums и отдельные hashes подписанных помощников. Затем проверяется ad-hoc подпись и создаётся ZIP. Прежний пакет при повторной сборке сохраняется под другим именем. Для распространения с Developer ID и нотариализацией нужна отдельная подпись Apple. Intel-сборка этим скриптом не заявляется.

Версия 0.3.1 использует форк `03bfd922c1749b27769a3e3a5680efde64d45af0` в прежнем внешнем TCP-режиме. После `tinc init` приложение восстанавливает права 0700 у каталогов идентичности: новый upstream выставляет 0755, несовместимые с приватным socket broker. Ключ устройства при обновлении сохраняется.

## Проверка

```sh
# Для некоторых тестов нужны локальные TCP/Unix-сокеты.
QUANTWAY_TEST_TINC="$PWD/bin/quantway-macos-client/Quantway.app/Contents/Helpers/tinc" \
  go -C mobile test ./clienttinc ./linux/account ./linux/subscription ./linux/desktopmeta ./linux/cmd/quantway ./macos/...

swift test --package-path mobile/macos --build-system native

# Тесты интерфейса с фиктивным мостом, без реального аккаунта и VPN:
QUANTWAY_NODE_MODULES=/path/to/node_modules node mobile/macos/tests/ui-smoke.cjs
```

Проверки включают преобразование IP-пакетов в обе стороны, стабильность ключа Tinc, запуск настоящего daemon на пакетном FD, запрет script hooks, обработку Mux и владение сокетами, проверку UID IPC, протокол кабинета и сценарии интерфейса. Они не доказывают работу PF, DNS и маршрутов с настоящей подпиской на конкретной версии macOS. Результат системной приёмки фиксируется отдельно в отчёте и `BUILD-RESULT.json` рядом со сборкой. Версия 0.2.11 прошла два живых подключения Tinc с проверкой обычных HTTPS и DNS после исправления остановки пакетного адаптера при ENOBUFS. Обычный режим Xray/AWG этой живой приёмкой не проверялся. Версия 0.3.0 прошла 18 проверок снимков упакованного интерфейса и чтение реальных данных кабинета; новое живое подключение VPN для переноса дизайна не выполнялось.

Диагностика включает число активных/пиковых/созданных внутренних TLS-соединений и время последнего полученного ответа. Публичные диагностические события сохраняются в `~/Library/Application Support/Quantway/Diagnostics/connection.jsonl` с правами 0600. Там нет cookie, ссылок подписки, токенов или ключей. Статус системной приёмки описан в `docs/audits/2026-11-03-macos-desktop-client.md`.

## Владение дескриптором Xray в 0.3.2

Xray закреплён на `syntr0x79/Xray-core` commit `cf54a5a2cafce1dac1aaf1ca7eb19ff145030dee`. Для переданного TUN он создаёт собственный CLOEXEC-дубликат и закрывает только его. Повторный Close безопасен; поздняя сборка мусора не закрывает дескриптор приложения или следующего назначения. Ранее изолированный UDP-тест снова выполняется вместе с остальным пакетом в одном процессе.

Сборщик проверяет выбранный модуль, архивы и исходники по контрольным суммам. Помощники и встроенный framework используют одно исправление; framework пересобирается при изменении fingerprint зависимости. В `Contents/Resources/Licenses/XrayDarwin/` включены manifest, лицензия, исходники и patch.

Подтверждённая смена страны теперь передаётся действующему помощнику без перезапуска процесса и системного TUN. Диагностическая принудительная сборка мусора включается только отдельным параметром приёмочного запуска; обычный интерфейс его не включает. [Живая приёмка 0.3.2](../../docs/audits/2026-11-04-macos-xray-fd-and-transitions.md) прошла PL→SE→PL и автоматическую замену PL-выхода в одном процессе/TUN, с GC и проверкой HTTPS/DNS/внешнего IP на каждом этапе.
